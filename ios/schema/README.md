# Aware Lab record contract v1

All UTF-8 JSON/JSONL resides in Documents/Runs/<runID>/ and is retrieved over USB. Schema v1 is the observation contract for G1, M4 discovery and M5 AccessorySetupKit observation; no data-plane or throughput pass is emitted by the App.

- configuration.json: runID (safe filename, max 100 ASCII characters), experimentID, directionID, discoveryTimeout (2–30 seconds by default; above 30 only with `AWARE_LONG_WAIT_APPROVED`, up to 120 seconds for g1/m4/m5 and 600 seconds for the m4gate test), mode (g1, m4 or m5), targetName (M4 expected PSI name or M5 expected pairing name, max 64 characters without line breaks; default `identity.pairing_name` from `config/wirelessd.toml`), service. Only these test settings may be injected; no endpoint, permission, connection, PIN or success override exists.
- events.jsonl: schemaVersion=1, runID, experimentID, directionID (IOS-XCUITEST-G1, NAN-DISCOVERY-DUAL or NAN-PAIRING-DUAL), source=ipad.app, version, sequence (1-based), monotonicNS (DispatchTime uptime nanoseconds on this iPad), wallTime (UTC ISO8601, seconds), action, state, detail. M4 runs add one `m4_target_expected` event after `launch`. M5 runs add one `m5_target_expected` event after `launch` and record exactly `launch`, `m5_target_expected`, `capability_check`; the ASK session itself is recorded in `ask-session.json`.
- result.json: schemaVersion=1, runID, source, status=BLOCKED, stage (G1-observation, M4-discovery-observation or M5-pairing-observation), state, reason, wirelessVerified=false, throughputVerified=false. App results never certify UI visibility or pairing; XCTest independently asserts the real system UI.
- mac result.json: return codes, validated_app_runs, validation_errors, scope=UI only. PASS certifies the assertions and exported evidence for that invocation, not all G1 (sysdiagnose is a separate requirement). For `--profile m4`, PASS additionally requires `m4-validation.json` and `nan-summary.json`; it does not certify that a publisher was discovered. For `--profile m5`, PASS additionally requires `m5-validation.json`, `m5-evidence.json` and `nan-summary.json`; the observation and snapshot tests do not certify that the board was listed or that the system paired anything. The Stage A test additionally requires a target-row tap, a PIN entry attempt/submission, an authorized accessory with a non-zero WiFiAwarePairedDeviceID present in the WAPairedDevice snapshot, and a clean PIN leak check; it still does not certify board-side PASN or G5-P. For `--profile m4gate`, PASS requires `gate-validation.json`: one gate-result attachment with 10 cycles (or 1 cycle when `--gate-ttl` measures TTL), per-cycle on/off screenshots and trees, monotonic transition times, `device_tap_count=0`, and `pairing_flow_started=false`. The 10-cycle mode requires `final_target_absent=true`; the single-cycle TTL mode records `final_target_absent=false` when the target is still present after the configured wait and treats it as a lower bound.

State path currently implemented for G1/M4: idle → ready → discoveryRequested → cancelled / timedOut / endpointSelected. Capability or recording initialization errors → failed. An endpoint selection is explicitly not connected. M5 keeps the G1/M4 session state for capability checks and exposes a separate pairing state: idle → activating → ready → pickerRequested → pickerPresented → pickerDismissed / authorized / invalidated / failed. Only `authorized` with a non-zero `wifiAwarePairedDeviceID` is pairing evidence; a presented picker, a PIN prompt or a dismissed picker is not. Connecting, throughput, warmup and finished transfer states are not implemented.

### M5 AccessorySetupKit session (ask-session.json)

Written by the App in M5 mode and validated by `check_m5_evidence.py`; the JSON Schema is [ask.schema.json](ask.schema.json).

- Identity: schemaVersion=1, runID, source=ipad.app, directionID=NAN-PAIRING-DUAL, appVersion, supportedTechnologies (read back from `NSAccessorySetupKitSupports`), pinHandling=system_picker.
- descriptor: the exact `ASDiscoveryDescriptor` values used by the picker (`_fileserver._tcp`, role subscriber, vendor and model from the publisher identity configuration, display item name, expected pairing name). The role follows the app's own Wi-Fi Aware declaration (`Subscribable`); the accessory remains the publisher. Vendor and model must match the publisher SDF; `AWARE_VENDOR_NAME` and `AWARE_MODEL_NAME` override the defaults for a deployed device.
- session: activated, activation/invalidation times, picker requested/presented/dismissed times, picker completion error, and accessory added/changed/removed counts. The App cannot distinguish a person's cancellation from a discovery timeout; it records the observed conclusion, not a presumed intent.
- accessories: displayName, state (unauthorized, awaitingAuthorization, authorized, unknown), WiFiAwarePairedDeviceID, and whether an SSID or Bluetooth identifier is present. Bluetooth identifiers themselves are not logged.
- pairedDevices: WAPairedDevice snapshot (id, name, pairingName, vendorName, modelName). `pairedDeviceSnapshotError` records a failed `WAPairedDevice.allDevices.current()` read.
- events: ordered ASK lifecycle and accessory events with sequence, monotonicNS, wallTime, event name, optional eventCode, optional accessory snapshot and optional error. The App never writes a PIN, key or pairing secret.
- outcome: not_started / session_ready / picker_requested / picker_presented / picker_failed / picker_dismissed_without_accessory / picker_dismissed_with_accessory / accessory_observed / authorized. Precedence is authorized, picker_*_error, dismissed, accessory observed, presented, requested, activated. The validator recomputes it; a mismatch is an error.
- An authorized accessory must have a non-zero WiFiAwarePairedDeviceID and that ID must appear in `pairedDevices`; otherwise the evidence is incomplete.

### M5 XCUITest evidence

`<runID>-m5-result` JSON attachment: mode=m5, test (`accessory_picker`, `paired_device_snapshot` or `stage_a_pairing`), target/service/descriptor values, picker request/presented/dismissed flags, observed state history, accessory and paired-device IDs read from App labels, target candidates seen in the system tree, `device_tap_count`, `pin_entry_attempted`, `pin_handling=system_picker`, wait/time fields and `failure`. The observation and snapshot tests keep `device_tap_count=0` and `pin_entry_attempted=false`; Stage A requires a tap and a PIN attempt for success. Screenshots and trees are `<runID>-ask-observation`, `<runID>-ask-pin` (Stage A, PIN UI before typing) and `<runID>-ask-final`; `check_m5_evidence.py` requires the observation pair for every test, the final pair for picker and Stage A runs, and the PIN pair when Stage A found the PIN UI. A final screenshot may be withheld when a non-secure PIN field still contains text; the redacted tree and the `screenshot_withheld_due_to_unmasked_pin` flag remain. A reported failure invalidates the run. Cross-checks reject evidence where XCTest reports a picker, authorization or ID that the App record does not contain.

### M5 Stage A PIN evidence

- The ASK picker first presents a "Find Accessories" / "查找配件" gate; the Stage A test taps that system button before waiting for the target row. A pure Wi-Fi Aware descriptor with role `subscriber` is accepted without Bluetooth fields; actual listing of a publisher still requires the publisher to be present.
- `run_tests.py --pin <6 digits>` requires `--profile m5` and the Stage A test (it selects that test when `--only` is absent). The PIN is placed only in the `AwareLabUITests` xctestrun environment as `AWARE_M5_PIN`; the App process does not receive it and no App API reads it.
- The transient injected xctestrun is deleted immediately after `xcodebuild` returns. The Stage A test reads `AWARE_M5_PIN`, taps only a row matching the pairing name (`AWARE_TARGET_NAME` or the configured default) or service name (`_fileserver._tcp`), types the PIN digit by digit into the system field, and submits it with a labelled system button or keyboard Return. It never writes the PIN to an App record, an attachment string, a failure message or a JSON field; `pin_length` is the only PIN-derived value in evidence.
- Trees and alert/failure strings are redacted by the test. After the test, `run_tests.py` stops the system-log collector, redacts the literal PIN from text evidence (`pin_safety.py`), and removes `tests.xcresult` if its bytes contain the PIN. The device-level `failure.png` is not captured for Stage A. Screenshots are taken before typing and after submission; if a non-secure field still contains text, the final screenshot is withheld and recorded.
- `check_m5_evidence.py` reads `AWARE_M5_PIN` from its environment (not argv), scans text evidence for the literal, and reports `pinLeakCheck` (`performed`, `clean`, `matchCount`, relative `files`) without echoing the PIN. Stage A evidence without the environment variable is rejected because the leak check could not run.
- Stage A waits are event/completion driven; each has a 5 s failure fallback (picker present, Find Accessories, target row, PIN UI, authorized, paired-device snapshot). The overall subprocess fallback is 30 s. Evidence records `started`, `picker_requested`, `picker_presented`, `picker_search_tapped`, `target_found`, `target_tap`, `pin_ui_found`, `pin_typed`, `pin_submitted` and `result` wall/monotonic times, the target query, PIN UI scope, submit method, alert/PIN-error observations and the picker/authorization state history.
- Failure categories: `picker_not_presented`, `ask_failed`, `target_not_listed`, `target_not_hittable`, `pin_ui_not_found`, `pin_rejected`, `authorized_timeout`, `authorized_without_paired_device_id`. A failed Stage A run keeps its screenshots/trees and fails validation with the category; a successful run requires `pin_entry_attempted=true`, `device_tap_count>=1`, `authorized=true`, non-zero accessory/secondary IDs and a complete paired-device snapshot.

The system picker provides no public SwiftUI cancellation/error callback. The App records its own control container close and deadline, and does not fabricate an underlying framework error. XCTest observes system-owned labels and close action separately. Endpoint metadata is not logged. UI observations reside as named xcresult attachments, including the exact runID.

Lifecycle I/O uses a serial utility queue and fsync at each lifecycle event. There is no packet logging, receive loop, throughput calculation or overhead benchmark yet. Host and iPad monotonic clocks are distinct domains: correlate by runID and wall-time anchors, never subtract them. Wall time is not suitable for throughput. System log privacy redaction/loss is not corrected or interpreted as success.

The exporter currently copies the Runs directory to preserve raw history, but accepts only the exact expected run IDs. It checks sequence continuity, monotonic ordering, expected actions and cancelled result, a matching system log record, and named UI result/screenshot attachments. A duplicate run ID is rejected on device, never silently appended. M4 runs additionally require `m4-result`, `system-tree` and `system-discovery` attachments, plus `target-found` only when the target was observed; an absent target is recorded as evidence, not as a test failure. `check_m4_evidence.py` performs that validation and `parse_nan_log.py` summarizes the same run's system log.

`parse_nan_log.py` additionally emits `askObservations` (heuristic counts for AccessorySetupKit wording, PIN-like lines redacted) and `askPatterns`; these do not change the M4 NAN discovery counters. Missing ASK log lines are not interpreted as absence of the system flow.

Future cross-end contract: record localPerformanceMode and peerPerformanceMode separately; unknown peer mode must remain unknown. Agreement must be verified before performance testing (see plan/INTEROP_MATRIX.md when available). No M7 mode is selected by G1.
